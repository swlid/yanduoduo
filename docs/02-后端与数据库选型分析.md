# 后端与数据库选型分析（待用户选择）

> 日期：2026-08-31
> 目标：在已确认「微信小程序 + Web 管理后台 + Redis」的前提下，比较 Python/FastAPI 与 Node.js 后端，以及 PostgreSQL 与 MySQL 数据库，给出推荐。

## 一、后端：Python + FastAPI vs Node.js

### 1. 对比总表

| 维度 | Python + FastAPI | Node.js（NestJS / Fastify） |
| --- | --- | --- |
| 语言/生态 | Python 生态强在数据、爬虫、ETL、统计、LLM | JavaScript/TypeScript 生态强在 Web、I/O、前后端同构 |
| API 开发效率 | 高：FastAPI 自动生成 OpenAPI 文档，Pydantic v2 强校验 | 中到高：NestJS 结构化强，但模板代码偏多 |
| 数据清洗/导入 | 非常强：pandas、openpyxl、csv、xlrd 等成熟 | 一般：xlsx/exceljs 可用，但数据分析生态较弱 |
| 类型/模型迁移 | SQLAlchemy 2 + Alembic 成熟、严谨 | Prisma / TypeORM / Drizzle 可用，迁移稳定性和 SQL 控制不如 Alembic 精细 |
| 异步与并发 | FastAPI 异步 + Uvicorn，够用；CPU 密集需 worker | 天然异步 I/O，适合高并发 API/推送 |
| 实时推送 | 可用 WebSocket/SSE，生态中等 | 非常自然，WebSocket/SSE 成熟 |
| 未来接入 AI | Python 是 LLM SDK/工具链第一选择 | 可接，但很多 AI 工具链以 Python 为主 |
| 团队/维护成本 | 若团队懂 Python，维护成本低 | 若团队懂 TypeScript，可全栈统一 |
| 适合场景 | 结构化数据 + 导入清洗 + 规则计算 + 后续 AI | 高并发实时交互、前后端同一语言 |

### 2. 针对本项目的结论

本项目核心瓶颈不是高并发，而是：

1. 大量院校/专业/招录数据清洗、CSV/Excel 导入、指标计算与趋势统计；
2. 后续要接入 LLM 择校问答和计划生成；
3. 数据质量、审核、溯源要求高，后端需要强校验和稳定迁移。

因此 **推荐 Python 3.12 + FastAPI**。它的自动接口文档、Pydantic 校验、SQLAlchemy/Alembic 迁移、pandas/openpyxl 数据导入能力，最贴合本项目。

如果团队更熟悉 TypeScript，或者未来希望前后端都用 TypeScript、重视实时推送，再选 Node.js + NestJS。技术上两者都能完成本项目，差别主要在未来迭代和团队效率。

## 二、数据库：PostgreSQL vs MySQL

### 1. 对比总表

| 维度 | PostgreSQL | MySQL |
| --- | --- | --- |
| JSON/扩展字段 | JSONB 成熟，可索引、可查询，适合 `metrics` 扩展指标 | JSON 可用，但函数和索引能力弱于 PostgreSQL |
| 复杂查询/统计 | 窗口函数、CTE、高级聚合强，适合分数区间、报录比、趋势分析 | 基础 SQL 强，复杂分析表达相对繁琐 |
| 数据完整性 | 约束、事务、类型系统更严格 | InnoDB 可靠，适合常规 OLTP |
| 全文检索 | 内置能力较强，可扩展 | 有 FULLTEXT，但中文分词通常要额外处理 |
| 时区/时间 | timestamptz 明确 | 时区处理历史坑较多，需要约定好 |
| 索引能力 | 支持部分索引、表达式索引，筛选性能优化空间大 | 索引成熟，但高级索引能力较弱 |
| 部署/托管成本 | 常见云数据库均支持，费用相当 | 最常见，云服务成熟，运维资料多 |
| 学习/运维 | 偏严谨，初期稍陡 | 最普及，教程多、上手快 |

### 2. 针对本项目的结论

本项目数据模型的关键点是：

1. `admission_stats.metrics` 用 JSONB 承载未来新增指标；
2. 多条件组合筛选（地区 × 层次 × 专业 × 科目 × 分数范围 × 难度指标）；
3. 报录比、复录比、分数线趋势等聚合统计。

这些场景下 **PostgreSQL 更合适**。JSONB 可以一边保证主表结构稳定，一边支持灵活指标；窗口函数和高级索引更利于复杂筛选和统计分析。

如果你们已有 MySQL 运维体系，或者希望完全沿用团队最熟悉的 MySQL，也可以选用 MySQL，但需要把 `metrics` 做成分表或 EAV，扩展性和查询表达力会弱一些。

## 三、推荐组合

**FastAPI + PostgreSQL + Redis**：

- FastAPI：自动文档、强校验、导入清洗和未来 LLM 接入最顺。
- PostgreSQL：JSONB 指标扩展、复杂筛选统计、数据完整性最佳。
- Redis：缓存筛选结果、会话、限流、延迟提醒。

这是一套稳定、通用、可本地用 Docker Compose 跑通的组合。
