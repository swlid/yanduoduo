## 0. 一句话结论

首版采用「微信小程序 + Web 管理后台 + FastAPI 单体后端 + PostgreSQL + Redis + 文件导入/人工录入的 Mock 与真实数据双通道」方案。数据模型严格按「院校—专业—年度—指标」设计，让后续接真实数据、扩展调剂/导师/就业时只增不改。里程碑 1 只交付方案与样例数据字典，不写业务代码。

## 1. 需求边界与范围确认

### 1.1 首版必须做（P0，对应 MVP 和主流程闭环）

1. 院校库：院校基础信息 + 专业目录 + 历年招录指标 + 初试/复试信息。
2. 查询与筛选：地区、层次、类型、学科门类、专业、科目、分数区间、难度指标组合筛选。
3. 院校/专业详情页与「院校 × 专业 × 年份」横向对比。
4. 收藏夹与目标院校清单。
5. 择校测评：生成个人画像，输出「冲刺 / 稳妥 / 保底」三梯度推荐及理由。
6. AI 择校问答：自然语言提问，回答必须引用数据来源、年份与不确定性。
7. 全流程时间线与关键节点提醒：动态定位当前阶段、关键节点、提前 N 天提醒和操作指引。
8. 阶段任务模板：基础期 / 强化期 / 冲刺期 / 复试期默认任务清单。
9. 学习规划与打卡：目标分数拆解、分阶段计划、每日任务、打卡、补卡、顺延、进度可视化、周/月报告。
10. 管理后台：院校/专业/招录/考试数据录入、编辑、审核、CSV/Excel 批量导入、来源标注、用户勘误、资讯/政策发布。

### 1.2 首版刻意不做（P2 / 后续里程碑）

- 真实大规模爬虫与全量数据接入：仅预留数据接口与采集规范。
- 调剂信息实时聚合、导师库、就业去向库：模型预留扩展点，不在首版实现。
- 社区/论坛、真题下载交易、付费会员与支付体系。
- 复杂推荐算法（协同过滤等）：先用规则 + 数据统计，后续再升级。
- 在职考研、同等学力、少干计划等细分人群的深度差异化规则。

### 1.3 核心用户故事与验收口径

| 用户目标 | 关键路径 | 验收口径 |
| --- | --- | --- |
| 了解某校某专业难不难 | 首页搜索 → 筛选 → 院校/专业详情 | ≤3 步看到近 3 年报录比、分数线、复录比、来源和更新时间 |
| 对比 3 所院校 | 收藏/勾选 2-4 个组合 → 对比页 | 一个页面并排展示核心指标 |
| 知道自己该冲哪些学校 | 测评 → 个人画像 → 三梯度推荐 | 每个推荐附带至少 1 条可追溯的数据理由 |
| 不错过报名和初试 | 首页时间线 → 节点提醒订阅 | 按当前日期显示当前阶段、下一个节点、剩余天数和操作指引 |
| 能坚持计划 | 生成计划 → 每日打卡 → 查看周报 | 自动生成每日任务，漏打卡可补卡/顺延，进度可见 |

## 2. 系统整体方案

### 2.1 架构总览

```text
学生端（微信小程序）
        │ HTTPS / REST
        ▼
FastAPI 单体服务
  ├─ API 层：认证、院校、专业、测评、计划、打卡、节点、资讯、勘误
  ├─ 服务层：筛选查询、择校规则、计划生成、提醒调度、AI 问答编排
  └─ 数据访问层
        │
        ├── PostgreSQL：结构化业务数据
        ├── Redis：缓存、会话、限流、任务队列/延迟提醒
        └── 对象存储：图片/文档等非结构化附件（首版可本地或 MinIO）

管理后台（Web，Vue/React）
        │ HTTPS / REST
        └── 同一套 FastAPI，/admin 权限域

外部能力
  ├─ LLM API：AI 择校问答、计划生成
  ├─ 推送：微信订阅消息/模板消息
  └─ 数据源：官方公开数据 → 采集脚本/批量导入 → 人工审核
```

### 2.2 技术选型与理由

| 模块 | 选择 | 理由 | 备选 |
| --- | --- | --- | --- |
| 学生端 | 微信小程序（原生 TypeScript 或 uni-app） | 获客成本低、符合学生使用习惯、支持订阅消息；uni-app 可复用 H5 | Taro |
| 管理后台 | Web（Vue 3 + TypeScript + Element Plus） | 表格/表单/批量导入开发效率高 | React + Ant Design |
| 后端 | Python 3.12 + FastAPI | 生态适合 LLM 接入与数据清洗；自动 OpenAPI；异步性能够用 | Flask（首版偏重工具，FastAPI 更合适） |
| 数据库 | PostgreSQL 16 | JSONB 支持灵活字段，适合「年度指标」扩展；事务与权限强 | MySQL |
| 缓存/队列 | Redis 7 | 缓存筛选结果、会话、限流；延迟任务可用 ZSET 或 RQ | RabbitMQ（首版暂不引入） |
| ORM/迁移 | SQLAlchemy 2 + Alembic | 稳定、类型友好、迁移可追溯 | Tortoise |
| 数据校验 | Pydantic v2 | 与 FastAPI 天然集成，导入数据强校验 | — |
| AI 能力 | LLM API + 本地规则兜底 | 问答与计划生成需要结构化约束，先做规则/RAG 提示词 | 自建模型（不做） |
| 数据采集 | 脚本 + CSV/Excel 批量导入 + 人工审核 | 先保证功能闭环，合规采集逐步接入 | 直接爬库（不合规、不稳定，不做） |
| 部署 | Docker Compose（API + DB + Redis + Admin） | 本地可复现，里程碑阶段便于验收 | K8s（上线后再考虑） |

### 2.3 数据策略（重要）

**首版原则：功能闭环优先，Mock 数据先行，真实数据按「批次 + 来源 + 年份」增量接入。**

1. Mock 数据：用于跑通筛选、详情、对比、测评、计划、打卡、提醒全部流程。
   - 覆盖约 20-30 所典型院校，包含 985/211/双一流/普通、综合/理工/师范/财经/医药等类型。
   - 覆盖计算机、电子信息、机械、金融、教育学、临床医学等 8-15 个常见专业。
   - 每个「院校—专业」组合至少准备 3 个年份的招录指标（2023-2025），并显式标记 `data_quality=mock`。
   - Mock 数据不展示为真实事实，页面显示「示例数据，仅供参考」。
2. 真实数据：先人工录入少量公开、可核实的数据，再逐步增加合规采集脚本。
   - 来源优先级：研招网 > 院校研究生院官网 > 省级考试院 > 可信第三方（仅补充）。
   - 每个字段必须带 `source_url`、`source_name`、`source_year`、`collected_at`、`review_status`。
   - 采集必须遵守 robots、限速、不登录、不绕过反爬；第三方只做补充并注明出处。
3. 数据更新与纠错：用户可提交勘误；后台人工审核后形成新版本记录，历史版本可追溯。

## 3. 数据模型设计

### 3.1 设计原则

- 遵循「院校—专业—年度—指标」骨架：院校和专业是主数据；年度和指标是事实数据。
- 所有事实数据都有「来源 + 年份 + 更新时间 + 审核状态」，可追溯、可纠错。
- 指标统一存为「键值 + 数值/文本 + 单位 + 来源」，避免每个新指标都加列。
- 考试科目用可扩展的结构化字段，而非一列拼装字符串。
- 用户域与业务域分离；计划、打卡、提醒都可独立演进。

### 3.3 关系简述

```text
institutions 1 ─── n institution_majors n ─── 1 majors
                        │
                        n
                        │
                 admission_stats（每年一行，多指标）

users 1 ─── n assessments 1 ─── n recommendations n ─── 1 institution_majors
users 1 ─── n favorites / target_list
users 1 ─── n plans 1 ─── n plan_tasks
users 1 ─── n check_ins
process_nodes n ─── n users（订阅关系）
```

## 7. 明确标注的假设

- 产品名暂定「研多多」，最终可改，代码内使用稳定英文代号 `yanduoduo`。
- 初试日期按每年 12 月下旬常规规则估算，官方发布后可回填；提醒默认提前 7 天，可配置。
- 推荐逻辑首版采用「画像匹配 + 历史指标阈值 + 可解释规则」，不追求高级算法。
- 计划生成首版允许「模板 + 目标分数拆解 + 用户当前水平」生成，AI 只做增强，不是唯一路径。
- 数据展示必须包含「年份、来源、更新时间、示例数据标识」；Mock 与真实数据在界面上明确区分。
